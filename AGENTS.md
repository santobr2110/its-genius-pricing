
- Observability pricing has two isolated models (classic UM bands vs levels M1–M4 + NVPS) selected by `modeloObservabilidade`; only one ever produces monitoring cost — keeps saved pricings unchanged.
- Smart ITO fiscal mappings live centrally in app_defaults and are resolved by the highest active tier plus contracted level through pricing/itoFiscal; ITSMContext applies resolved taxes globally and snapshots fiscalITO in calculator state. Saved historical quotes are never migrated implicitly; frozen taxes survive profile merges, and explicit application refreshes a quote — prevents changes to old pricing while keeping live drafts tied to the central registry.
- Shared pricing lives in `src/lib/pricing/`: every offering computes the markup-divisor cascade through `cascataNucleo` with its own declared `REGRA_*` edge rule (Σ ceiling, divisor form, sum order) — rules reproduce historical results and must not be harmonized. Tax rates for every offering come only from the central registry: each product (`tax_product_codes`) links to a LC 116 service code (`service_codes`: PIS/COFINS per code, `service_code_iss`: ISS per municipality) and inherits its rates; `tax_product_code_rates` is used only when `usa_aliquota_propria` (exception) — `useTaxCodes` merges both into effective per-product `rates` via `aliquotasEfetivas`, so `resolveTaxRates`/`ProdutoFiscalCard` stay unchanged; one place to maintain rates shared by many products; the legacy static/localStorage code table was removed — one official source, managed in Admin ("Cadastro tributário de produtos"). Each code carries `ofertas`  and `ProdutoFiscalCard` takes an `oferta` prop to list only codes tagged with that offering (a code may serve several; untagged codes appear nowhere); `catalog_products` is deprecated — one product/tax registry, no duplicates.
- `src/test/naoRegressao.test.ts` snapshots Smart ITO, BodyShop and M1–M4 results; never update those snapshots to make a change pass — protects existing pricing.
- Treinamento catalog (courses, proposal content, combos, params) lives in `training_*` tables, read via `useTreinamentoCadastro`, gated by `page.trn.view` (read) / `page.trn.admin` (write) in RLS; pure helpers in `src/lib/treinamento/` — keeps official course data and pending-confirmation flags in one auditable place.
- Treinamento pricing: pure engine in `src/lib/treinamento/calc.ts` + `carrinho.ts` (tested in `treinamentoCalc.test.ts`); drafts/quotes live in `pricing_presets` with group `observabilidade`/offering `treinamento` via `useTreinamentoCotacoes` (Smart ITO's `usePricingPresets` left untouched) — avoids regressions in existing offerings.

- Treinamento: o SKU fiscal de cada condição de venda (Turma Aberta, In Company, Somente exame) fica em `training_params` (`produto_*`), editado em Financeiro › Impostos & Markup, não no cadastro do curso — a condição é escolhida em cada venda.
- Subscrições Zabbix (preço fixo por SKU) calcula o valor de chegada via `decomporVenda` em `src/lib/pricing/chegada.ts`; `aplicarDesconto` do Treinamento é um wrapper fino dele, provado equivalente em `chegadaEquivalencia.test.ts` — uma só conta de chegada para as duas ofertas.
- Subscrições Zabbix catalog (SKUs, proposal content, params) lives in `zabbix_*` tables, read via `useZabbixCadastro`, gated by `page.zbx.view` (read) / `page.zbx.admin` (write) in RLS; pure helpers in `src/lib/zabbix/calc.ts` — mirrors the Treinamento pattern so each offering stays isolated.
- Zabbix SKU discounts (ro/sem_ro/pgto30_*) are optional overrides: NULL inherits `zabbix_params.desconto_*_<categoria>` via `resolveDescontos` (0 is a real value) — one place to change category discounts without touching each SKU.
- Zabbix quotes freeze every calc input in `payload.snapshot` on save (`congelar`); a saved quote recalculates from the snapshot (`entradasDoSnapshot`), never the live catalog, until the user re-evaluates — cost depends on FX and partner discounts that change. Engine in `src/lib/zabbix/carrinho.ts` (tested in `zabbixCalc.test.ts`); quotes via `useZabbixCotacoes` (offering `subscricoes-zabbix`).
- Zabbix proposal: one pure model (`montarModeloProposta` in `src/lib/zabbix/proposta.ts`) feeds the on-screen preview/PDF (`PropostaDoc`) and the Word (`propostaDocx.ts`, built with `docx`, no template); emissions store that frozen model in `payload.emissoes` and only emit from an intact snapshot — preview, PDF and Word can never disagree. Proposal texts live in `zabbix_params` (`proposta_*`); empty renders as [A CONFIRMAR].
- Zabbix proposal Word v2 fills `public/templates/proposta-zabbix-template.docx` via docxtemplater (`src/lib/zabbix/propostaDocxV2.ts`); `gerarPropostaZbxDocx` dispatches by `modelo.layoutVersao` (absent = legacy generator) — old emissions stay byte-identical, visual changes go in the .docx, never in code.
- Subdirectories have AGENTS.md: read src/pages/bodyshop/AGENTS.md for BodyShop. Its monthly engine shares live/frozen inputs and isolates quotes by offering; legacy stays frozen — prevents repricing.
